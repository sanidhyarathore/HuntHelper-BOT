PATCH 5 — fixes the actual bug behind the sustained 429s you hit.

Copy these 2 files into your tgjobs folder, overwrite when asked.
No .env changes.

ROOT CAUSE: Gemini's error message text is generic no matter which limit
you hit — it never says "day" or "daily" anywhere. The real signal (a
field called quotaId, e.g. "...PerDayPerProjectPerModel-FreeTier" vs
"...PerMinute...") is buried in the error body, which our code wasn't
reading at all. So a genuine daily-cap hit always looked identical to a
transient per-minute one, and got the wrong response: exponential
backoff and retries, instead of stopping immediately.

I verified the real error shape against live examples (Google's own
GitHub issue trackers) before writing this fix, rather than guessing
again after getting the model name wrong earlier in this project.

TWO layers now, in case Google changes their error format again later
(they already have, more than once this year):

  1. Classification reads the actual quotaId field, not just the
     generic message text.
  2. A circuit breaker: if 4 calls in a row fail for ANY reason, the
     run stops and treats it as a stuck quota/outage rather than
     grinding through your whole remaining backlog one doomed retry
     at a time. This works even if classification is ever wrong again.

Both were tested against realistic error shapes before shipping —
including one where classification is deliberately made to fail, to
confirm the circuit breaker catches it independently.

AFTER COPYING: run.py cycle / runme.bat as normal. If you're still
inside today's exhausted quota window, it'll now stop cleanly within
seconds instead of retrying for minutes, and print something like:

  "Daily API quota reached. Stopping this run — remaining messages
   are untouched and will run next time."

That's correct behaviour. Just run it again after quota resets
(Gemini resets around midnight Pacific time).
